# Node Banana 2.0 launch plan

Created 9 September 2026. Status: launch backlog; implementation and release approval are still outstanding.

This is the return point for work remaining after the desktop foundations in [PR #160](https://github.com/shrimbly/node-banana/pull/160). Merging that PR into `develop` integrates the preview; it does not publish version 2.0. Other feature work can continue separately and join the release candidate when ready.

## Release scope and decisions

| Item | Launch scope |
| --- | --- |
| Release | Node Banana **2.0.0**, with release notes explaining the move to an installable desktop app |
| macOS | **Apple Silicon / arm64 only**; signed and notarised app, drag-to-Applications DMG, and ZIP |
| Windows | **x64 installer** as the working assumption; signed NSIS `.exe`, validated on actual Windows hardware |
| Excluded builds | Intel Mac, Linux and Windows arm64; no universal Mac build |
| Distribution | Direct downloads linked from a landing page; GitHub Releases is the proposed artifact host |
| Existing users | Preserve workflow compatibility, the `Node Banana` profile, encrypted credentials, preferences and the default localhost origin |
| Provider access | Users bring their own keys; explain provider billing and which features need an internet connection |
| Updates | A documented, tested manual upgrade path is required. Automatic updates can follow 2.0 unless explicitly added to scope |

Confirm Windows architecture, supported OS versions, public domain, publisher identity, download hosting, and the release feature list before the release candidate. Determine minimum OS versions from the chosen Electron version and real testing, then use the same wording in the app, installers and website. No launch date is committed here.

## What is already in place

The 1.9.0 preview has isolated Mac packaging, an authenticated local backend, writable runtime provisioning, encrypted desktop credentials and explicit `.env` import, window persistence, backend restart, and checkpoint recovery with durable media. These are foundations to retain and verify on the final release, rather than tasks to rebuild.

The last review cycle passed 2,982 application tests, 16 Electron tests, Mac packaging and installed-app acceptance. Three specialist reviewers were clear. Those results apply to that preview revision, **not to future Windows or signed 2.0 artifacts**. See [the verification record](desktop-verification.md) for exact evidence and [the preview guide](desktop-preview.md) for current commands and behaviour.

## Launch blockers

Each unchecked item remains open. Add an owner, implementation PR and evidence link as work starts. Complete these before public downloads are announced.

### 1. Release builds and distribution

- [ ] Make `scripts/package-electron.cjs` support the two target platforms explicitly. It currently assumes macOS arm64, calls Apple's `iconutil`, uses Mac resource paths and disables signing. Split platform-specific icon, artifact and verification steps while retaining the clean build environment and allowlisted runtime inputs.
- [ ] Build Windows x64 on a Windows runner and Mac arm64 on a Mac runner. Verify the complete production dependency closure, including native modules such as `sharp`, for each target. Neither installed app should need Node, npm, Git or the source repository.
- [ ] Add repeatable release CI with an explicit two-platform matrix, lockfile installs, tests, production type checks, artifact validation and retained test results. Keep provider credentials and developer `.env` files out of release inputs. Supply signing credentials only to the signing steps, without printing or packaging them.
- [ ] Configure Mac Developer ID signing, hardened runtime and the required entitlements; notarise and staple the distribution. Test a browser-downloaded, quarantined DMG on a second Mac with no development setup. Verify the bundled utility process still starts after signing.
- [ ] Configure Windows publisher signing for the installer and applicable executables. Test signature verification and actual download/install behaviour on a clean machine. Record any SmartScreen behaviour; signing must not be presented as a guarantee of warning-free downloads.
- [ ] Keep application identity and the existing user-data location stable when signing and upgrading. Test that preview users can still decrypt their credentials after installing the signed build, including keychain prompts on Mac.
- [ ] Produce clearly labelled artifacts containing version, platform and architecture; publish SHA-256 checksums, release notes and minimum system requirements. Promote the exact tested artifacts rather than rebuilding after acceptance.
- [ ] Stage a draft release and validate download links before publication. Keep a known-good release available and document how to withdraw a broken download without losing users' work.

Use the [Electron signing guide](https://www.electronjs.org/docs/latest/tutorial/code-signing) and [electron-builder Windows signing guidance](https://www.electron.build/docs/features/code-signing/code-signing-win/) during implementation. The repository currently pins electron-builder 26.15.3; verify options against that version before using examples from newer documentation.

### 2. Installer and desktop polish

- [ ] Polish the Mac DMG: dark banana artwork with no white border, readable layout, obvious drag-to-Applications instruction, correct volume name and icon, and no clipped labels at common display scales.
- [ ] Verify first launch from Downloads, installation to Applications, replacement of an existing version, launching while another copy is running, and launching after the DMG has been ejected. Provide a clear install-location prompt if running from the mounted image would cause problems.
- [ ] Polish the Windows installer: correct publisher/product/version/icon, progress and completion text, Start menu entry, optional desktop shortcut, and a working uninstaller. Prefer per-user installation without elevation unless a concrete requirement needs administrator access.
- [ ] Test Windows paths containing spaces and non-ASCII characters, user-selected drives, read-only folders, long paths, file locks and antivirus interference. Audit runtime provisioning, atomic file replacement, process shutdown and restart on Windows rather than assuming Mac behaviour transfers.
- [ ] Keep preferences, encrypted credentials and recovery data in the OS application-data location, diagnostics in the logs location, and workflow files in user-selected folders. Upgrades must preserve this data. Uninstall must leave workflows alone; deleting application data should be an explicit, clearly described choice.
- [ ] Check native window controls, drag areas, menus, keyboard shortcuts, focus, dialogs, DPI scaling, multiple monitors and display disconnection on both platforms, including credential and recovery screens before the editor opens.
- [ ] Make disk-full, unwritable profile, failed runtime provisioning, occupied port and disconnected-backend errors actionable. Verify Retry does not spawn duplicate processes or reset the graph.

### 3. Reliability, migration and providers

- [ ] Run successful, small provider requests using tester-entered keys in both installed builds. The automated preview check proved authentication rejection, not successful generation. Record model, date, platform, result and cost without recording the key.
- [ ] Define and test the provider/model combinations advertised for launch, including text-only and reference-image generation. Recheck model availability before shipping. Remove, disable or clearly explain unavailable models such as the Reve integration recorded in the preview verification; do not promise a provider feature on the basis of schema validation alone.
- [ ] Verify Windows credential encryption, restart persistence, import, update/delete and session-only fallback. Repeat Mac preview-to-signed-2.0 migration, including explicit draft clears, cancelled imports and unavailable secure storage.
- [ ] Address the legacy-media failure found in `Cars_new.json`: identify unavailable blob media by node, explain how to reattach it, and clearly indicate that recovery is not current. A generic `Failed to fetch` is insufficient for launch. Preserve the previous valid checkpoint and remaining graph; never silently claim missing media was recovered.
- [ ] Test old workflow save/load and round trips on both platforms, including external media and relocated folders. Provide a backup-and-migrate guide. Clearly distinguish a portable workflow from JSON that depends on files elsewhere on disk.
- [ ] Repeat large-workflow load, continuous edits, checkpointing and crash recovery with representative node counts and media sizes. Record peak memory, time to a completed checkpoint and disk growth. The current 68-node fixture is not a substitute for rerunning a representative several-hundred-node workflow.
- [ ] Exercise corrupt checkpoints, interrupted writes, disk exhaustion, missing media, app/renderer/backend crashes, explicit discard, cancelled close and interrupted generation. Verify no automatic job resubmission and no silent loss of tabs, paths, costs or viewport state.
- [ ] Test installing 2.0 over the preview and a candidate over an earlier candidate. Document a safe rollback route with data backups; do not assume older versions can read newer recovery or credential formats.
- [ ] Resolve or formally isolate the 203 existing repository-wide TypeScript test-fixture diagnostics with a tracked explanation and a check that prevents regressions. Repair the lint command/tooling and establish a meaningful passing release check; a green production build should not conceal unchecked test or development code.

### 4. Landing page and first-run experience

- [ ] Choose the domain and hosting, with HTTPS and an owner who can update downloads and announcements. Keep the landing page independently deployable from the local desktop server.
- [ ] Lead with a plain explanation of Node Banana and a current screenshot or short demonstration: create a workflow, connect providers and generate media visually. Show real 2.0 UI and representative outputs with permission to publish them.
- [ ] Make **Download for Mac · Apple Silicon** and **Download for Windows · x64** the primary actions. Platform detection may highlight a button, but both downloads must remain visible. Display version, system requirements and links to installation help, release notes and checksums.
- [ ] Explain bring-your-own-key setup, provider charges, local workflow storage, encrypted desktop credential storage and external API calls. Avoid blanket claims such as “fully offline” or “your data never leaves your machine.” State the actual pricing/licensing decision; the repository currently uses MIT.
- [ ] Include a short feature overview, a three-step getting-started guide, example workflows, FAQ, documentation and support links. Cover existing-user migration, missing media, recovery limits and manual upgrades.
- [ ] Test the page on mobile and desktop, keyboard navigation, focus visibility, text contrast, reduced motion, image alternatives, loading performance, social previews, metadata, and every download/help link. Show a useful alternative on unsupported devices.
- [ ] Align in-app onboarding with the page: select a provider, paste or explicitly import credentials, explain billing, choose a starter workflow, and complete the first generation. Keep cancellation, invalid-key and session-only flows clear.
- [ ] Ship a small set of tested starter workflows with redistributable assets and working provider defaults. Do not include private paths, credentials, expired blob URLs or expensive runs that start automatically.

### 5. Security, documentation and support

- [ ] Review the final Electron configuration against the [official security checklist](https://www.electronjs.org/docs/latest/tutorial/security): supported runtime/dependencies, renderer isolation, navigation and external-link handling, IPC sender validation, and local-server authentication. Include imported workflows and provider-returned content in the review.
- [ ] Repeat package and diagnostic scans for secrets and unintended user content on both builds. Document that credentials remain decrypted in renderer memory during use and that recovery content is not encrypted at rest.
- [ ] Publish accurate privacy/data-handling information and third-party notices with the MIT licence. State whether any telemetry or crash upload exists. Any collection added for launch needs an explicit product decision and suitable disclosure; local diagnostics are the current baseline.
- [ ] Update README, public documentation, screenshots, changelog and in-app version/help text for 2.0. Provide platform-specific installation, key setup, migration, backup, recovery, log access, uninstall and upgrade instructions.
- [ ] Establish a support route and issue template asking for app version, OS/architecture, steps and sanitised diagnostics. Explain that logs can be shared selectively and that credential files, workflow media and recovery folders should not be attached blindly.
- [ ] Assign a release/support owner, triage process and patch-release process. Include a documented way to get users security fixes even if automatic updates are deferred.

The landing page and documentation can progress alongside platform work once scope and download destinations are known. Do not publish the current unsigned 1.9.0 preview as the 2.0 release.

## Final release gate

- [ ] Launch blockers above are complete, with evidence and any remaining limitations explicitly accepted.
- [ ] Final Mac arm64 and Windows x64 artifacts pass clean-machine installation, upgrade, provider, save/load and crash-recovery checks. At least one tester other than the implementer completes first-run setup on each platform.
- [ ] The exact release commit passes the agreed tests, production build, type/lint checks and final code review; no known unresolved data-loss, credential-exposure or startup failures remain in supported use.
- [ ] Signing and download integrity are verified, final artifacts are staged, and rollback instructions have been rehearsed.
- [ ] Release notes, documentation, privacy information, support route and landing-page downloads are ready and agree on capabilities and limitations.
- [ ] Willie approves publishing **Node Banana 2.0.0**. Record the date, release commit, artifacts and acceptance links here when that happens.

## Later work, unless release testing makes it necessary

- Automatic updates and update notifications beyond the required manual upgrade path.
- Intel Mac, Linux, Windows arm64, app-store distribution and enterprise installers.
- Native workflow file associations and deep links.
- Moving all provider credential use out of the renderer.
- Optional crash reporting or product analytics, accounts, hosted sync and other services beyond local desktop use.
